Let the Database Say No

Almost every SQL-over-MCP server decides whether a query is safe by reading the query. That is a denylist made of string matching, and it is wrong the moment SQL grows a feature you did not think of. There is a better place to put the guard, and the database has been offering it for twenty years.

9 September 2026 · the first MCP server in this collection

I set out to build the smallest useful MCP server: read-only SQL over a SQLite file. Three tools, a row cap, done in an afternoon. The interesting part turned out not to be the protocol at all.

It was this question. When an agent sends you a statement, how do you decide whether to run it?

The answer everyone reaches for

Look at the SQL. If it starts with SELECT, run it. If it contains DROP or DELETE or UPDATE, refuse. Most published examples do some version of this, and it is the first thing anyone writes, myself included.

It is a denylist, and it inherits every denylist's problem: it has to anticipate. Consider what it must already handle correctly.

misses

WITH x AS (DELETE FROM t RETURNING *) SELECT * FROM x — starts with WITH, and in several engines that is a write.

misses

PRAGMA journal_mode = WAL — no forbidden keyword anywhere, and it changes the database.

misses

SELECT 1; DROP TABLE orders — starts with SELECT, if you only check the beginning.

refuses wrongly

SELECT * FROM shipments WHERE note LIKE '%DELETE%' — a keyword scan says no to a perfectly ordinary query.

You can fix each of these. You cannot fix the category. Every fix is a patch against a shape someone thought of, and the list of shapes is owned by whoever maintains the SQL dialect, not by you. Worse, the failure is silent in the direction that matters: nothing tells you when the guard has quietly stopped covering something.

The answer that does not have to anticipate

SQLite will answer the question for you. Two mechanisms, both older than the problem.

First, open the file read-only. Not a flag your code checks. The file is opened in a mode where writing is not a thing that can happen. 

con = sqlite3.connect(f"file:{path}?mode=ro", uri=True)

Second, install an authorizer. SQLite calls it before every action it is about to take, and hands you what the action is, which table, and which column. You return OK or DENY. 

_READ_ACTIONS = frozenset({
    sqlite3.SQLITE_SELECT,
    sqlite3.SQLITE_READ,
    sqlite3.SQLITE_FUNCTION,
})

def authorize(action, arg1, *rest):
    if action not in _READ_ACTIONS:
        return sqlite3.SQLITE_DENY
    return sqlite3.SQLITE_OK

con.set_authorizer(authorize)

That is the whole guard. It is an allowlist, so it is wrong only in the safe direction. It does not care how the statement is spelled, whether it uses a CTE, or what SQL adds next year. The engine that will execute the thing is the same one deciding whether it may.

The general form

Put the boundary where the system already enforces one. On a warehouse this is a read-only role granted on a narrow set of views, not a string check in your server. The lesson survives the change of engine; the regex does not.

It failed on my own code first, which is the point

I wrote the guard, then wrote schema(), which reads column information with PRAGMA table_info. It was refused. My own tool could not read its own schema.

This was the guard working. PRAGMA is a single authorizer action covering both table_info, which reads metadata, and journal_mode, which changes the database. It cannot be allowed wholesale. So the fix names the one pragma the tool needs: 

_READ_PRAGMAS = frozenset({"table_info"})

Sit with that for a second. A denylist would have let every pragma through, including the ones that write, and nothing would have failed. I would have shipped it. Deny-by-default failed loudly, in development, on the safe side. That is the entire argument for it in one incident.

The second thing I got wrong: refusals

Having refused something, how do you say so? The obvious move is to raise an error. The protocol has a perfectly good error channel.

It is the wrong channel. An error tells a model something broke, and the reasonable response to something breaking is to try again. But nothing broke. The server worked exactly as designed. What the model needs to know is not that it failed, but what to do differently.

So a refusal comes back as an ordinary, successful result that happens to say no:

{
  "refused": true,
  "guard": "not-read-only",
  "reason": "this database is served read-only; the statement asked to change it"
}

Two fields, two audiences. guard is a stable token, so code can branch on it and a model can recognise it without parsing English. reason is the sentence a person reads. The result is not an error, so nothing downstream treats it as a transient failure to retry.

GuardFires when
not-read-onlyThe statement asked to change something.
multiple-statementsA second statement tried to ride along after a semicolon.
table-not-allowedThe table is outside what this server exposes.
unreadable-databaseThe file could not be opened read-only at all.

The cap has to admit it is a cap

Every one of these servers limits how many rows it returns, because otherwise one careless query eats the entire context window. Fine. But a truncated result that does not say it was truncated is worse than no result, because the first page of an answer is indistinguishable from the whole answer. 

{"rows": [["ada"], ["bob"]], "truncated": true, "row_limit": 2, "elapsed_ms": 0.18}

elapsed_ms is there as a placeholder for the field that matters on a real warehouse, where it would be bytes scanned and money. A model cannot trade accuracy against cost when it has no idea what anything costs. On SQLite that is a rounding error. On Snowflake it is the whole bill, and the compute dwarfs the tokens by an amount that surprises people.

Was the server worth building at all?

Honest answer, for the case you are probably imagining: no. You at a terminal, with credentials you already have, should write the SQL. A server there is pure overhead, and this project had already reached that conclusion in writing about a different tool.

It changes when one of three things is true.

  • The consumer is not you. A colleague who does not write SQL, an agent running unattended, a client with no shell. The guards are what make handing it over acceptable.
  • The work is a loop. Why did last night's load drop by a third is fifteen queries, each depending on what the last returned. Pasting SQL back and forth fifteen times is unbearable.
  • The access needs governing. Someone other than you is asking, and there has to be a limit and a record.

Note that none of those three is about the protocol. They are about who is asking and how often. The protocol's contribution is narrower and still real: write the server once, and every client can use it. That is the problem it exists to solve, and it is why the specification compares itself to the language server protocol.

What I would tell someone starting

  • Build a server, not a client. The server side is where the design decisions are.
  • Point it at something the model cannot already reach. A database qualifies. A folder of text files does not, and you will conclude it was redundant.
  • Write the guards first. They are the product. The query execution is four lines.
  • Test the round trip, not the registration. Listing your tools proves nothing about what a consumer actually reads.

That last one caught a real bug for me. In the Python SDK, a tool annotated -> dict registers with no output schema and silently returns nothing structured. Annotated -> dict[str, object], it works. Nothing errors, nothing warns, and the tool looks identical in a listing. Only a test that goes through a client and reads the structured content catches it.
